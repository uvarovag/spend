# План реализации бизнес-логики: настоящее приложение (Redux Toolkit + локальная БД)

Пошаговый план превращения текущего UI (сейчас работающего поверх in-memory заглушки, теряющей всё при перезапуске) в полноценно рабочее однопользовательское офлайн-приложение на одном устройстве:

1. **Redux Toolkit** — реактивный слой состояния в памяти, заменяет самодельный `createStore`/`useStore` (`shared/lib/create-store.ts`, `shared/lib/use-store.ts`).
2. **expo-sqlite + Drizzle ORM** — настоящая локальная реляционная БД на устройстве, переживающая перезапуск приложения. Redux остаётся источником истины для UI (быстрые синхронные чтения, реактивность), SQLite — источником истины на диске (persistence поверх Redux, а не вместо него).
3. **Валидация форм и обработка ошибок записи** (Шаги 13–14) — закрывает открытые вопросы `docs/ux-guidelines.md` (молчаливый отказ форм при невалидных данных, незалогированные ошибки записи на диск), изначально оставленные без решения.
4. **Автоматические тесты и подготовка к релизу** (Шаги 15–16) — минимальный набор проверок и релизных артефактов, без которых результат остаётся работающим только на машине разработчика прототипом, а не рабочим приложением.

Технологический выбор по пунктам 1–2 зафиксирован: `AGENTS.md` («State management: Redux Toolkit», «Локальная персистентность: expo-sqlite + Drizzle»), `docs/app-overview.md` («Хранилище данных»), `docs/planned-features.md` (снят прежний запрет проектировать персистентность — теперь это явное решение, а не то, чего нужно избегать).

Ограничения, которым план не должен противоречить: `docs/data-constraints.md` (какие поля нельзя редактировать и почему — не зависит от способа хранения), `docs/planned-features.md` (offline-first синхронизация и совместное ведение семьёй — план ниже спроектирован так, чтобы не создавать для них архитектурных препятствий, но сам сетевой слой не реализует; это отдельный следующий этап, см. раздел «Что сознательно не входит» ниже).

## Архитектурные решения

### 1. Где живёт Redux-стор (снимает конфликт с правилом FSD «нижние слои не импортируют верхние»)

Слайсы (`createSlice`/`createEntityAdapter`) физически лежат в `entities/*/model` — это бизнес-логика. Сам `store`, типизированные `useAppDispatch`/`useAppSelector` и сборка редьюсера — в `shared/lib/store.ts`: это инфраструктура/wiring, а не бизнес-логика, поэтому по духу правила `shared: reusable, no business logic` это разрешено. `app/_layout.tsx` только оборачивает дерево в `<Provider store={store}>`, импортируя `store` из `shared/lib/store` (app → shared, разрешённое направление).

Сборка редьюсера: `shared/lib/store.ts` импортирует готовые редьюсеры из `entities/*/index.ts` (каждая сущность добавляет `accountsReducer`/`categoriesReducer`/`transactionsReducer` в свой публичный API) и собирает их через `combineReducers`. Формально это `shared`, импортирующий из `entities` — единственное осознанное отклонение от буквального правила направления импортов, принятое потому, что сборка стора — это композиция, а не бизнес-логика (аналогично тому, как `app/_layout.tsx` уже сегодня composes провайдеры из нижних слоёв). Более сложная альтернатива (`combineSlices` + ленивая инъекция, без этого импорта) даёт ту же практическую пользу только при большом числе слайсов, которых у нас всего три — усложнять ради чистоты правила не нужно (лишняя абстракция «про запас», см. `AGENTS.md` про lean code).

**Реальное отклонение, обнаруженное при реализации Шага 1 (важно для Шага 10):** если entity-файл (`use-accounts.ts` и т.п.) импортирует `store` напрямую из `shared/lib/store.ts` для недиспетчерских функций (`createAccount` и т.п.), получается циклический `require()` (`store.ts` → `entities/account/index.ts` → `use-accounts.ts` → `store.ts`), который Metro не резолвит безопасно — на реальном устройстве это падает с `Cannot read property 'accountsReducer' of undefined` при старте. Решение: `shared/lib/store-bridge.ts` — отдельный файл без единого runtime-импорта из `entities`, который берёт типы `AppDispatch`/`RootState` из `store.ts` только через `import type` (стирается на этапе компиляции, не создаёт цикл), и экспортирует `dispatch`/`getState`/`useAppDispatch`/`useAppSelector`. `store.ts` после создания стора вызывает `registerStore(store)` из `store-bridge.ts`, чтобы мост стал «живым» до первого диспетча. Entities импортируют `dispatch`/`getState`/`useAppSelector` из `store-bridge.ts`, а не из `store.ts` напрямую. **Тот же приём нужно применить и для `shared/lib/db.ts` на Шаге 10**, как только entity-файлы начнут импортировать `db` для write-through-записи — иначе повторится тот же цикл (`db.ts` → `entities/*/index.ts` → entity-файл → `db.ts`).

### 2. Где живёт локальная БД — тот же приём, что и со стором

- `shared/lib/db.ts` — открытие SQLite-соединения (`expo-sqlite`), сборка полной Drizzle-схемы (`drizzle(expo, { schema })`) и раннер миграций. По той же причине, что и `store.ts`, `shared` здесь импортирует определения таблиц из `entities/*/index.ts` (`accountsTable`, `categoriesTable`, `transactionsTable`) — то же принятое отклонение, что и для Redux, тем же обоснованием.
- Определение таблицы каждой сущности (`accountsTable = sqliteTable('accounts', {...})`) — в `entities/*/model/schema.ts`, рядом со слайсом. Столбцы 1-в-1 повторяют поля из `entities/*/model/types.ts`.
- Файлы миграций (генерируются `drizzle-kit generate`) — вне `src/`, в `drizzle/` в корне проекта (это артефакт тулинга, не код приложения — не часть FSD-слоёв).
- **Redux — единственный источник истины для UI, SQLite — write-through слой на диске:**
  - При старте приложения `shared/lib/db.ts` открывает БД, прогоняет миграции, читает все строки → этим гидрируется Redux-стор (один раз, до первого рендера экранов — см. Шаг 9).
  - Каждая мутация (`createAccount`, `updateTransaction`, …) синхронно диспатчит в Redux (UI обновляется мгновенно, как сегодня) и асинхронно пишет ту же мутацию в SQLite в фоне.
  - Это значит, что функции `create*`/`update*`/`archive*`/`delete*` **неизбежно становятся `async`/возвращают `Promise`** — если раньше это было временное упрощение in-memory заглушки, то настоящая запись на диск синхронной быть не может. Это единственное осознанное изменение контракта функций из `docs/app-overview.md` («сохранять сигнатуры функций как контракт») — meняются не параметры и не набор функций, а только `void → Promise<void>`. Список мест, вызывающих эти функции, нужно свести (Шаг 10) и убедиться, что ни один вызывающий код не полагается на синхронное завершение записи.

### 3. Судьба mock-данных

`entities/*/model/mock-data.ts` сегодня — это одновременно и «дефолтные данные приложения», и dev-заглушка. С настоящей БД это разные вещи:

- Реальное приложение должно стартовать **с пустой БД** у нового пользователя (0 счетов, 0 категорий, 0 операций) — это ожидаемое поведение настоящего финансового трекера, а не баг.
- `mock-data.ts` остаётся, но переквалифицируется в **дев-фикстуры**: используется только для сида БД в dev-режиме (`__DEV__`) или в будущих тестах, не попадает в продовую сборку как стартовые данные. Решить и явно закрепить на Шаге 8 — не переносить молча.

### 4. Настройки (тема/язык/последний счёт/черновик фильтров) — тот же паттерн, зеркально

Эти значения остаются на `createValueStore` (не переезжают в Redux — решение уже зафиксировано, см. `AGENTS.md`), но теперь тоже должны переживать перезапуск — иначе получится нелепо: операции сохраняются на диск, а тема каждый раз откатывается на дефолтную. Для них — не полноценная реляционная таблица (это не сущности с инвариантами и связями, а плоский набор пар ключ-значение), а **`expo-sqlite/kv-store`** — встроенный в `expo-sqlite` key-value слой с API, похожим на `AsyncStorage`, но поверх той же SQLite-БД (не тянет отдельную зависимость и отдельный файл БД). `createValueStore` дополняется чтением при инициализации и записью при `setValue` — тем же write-through приёмом, что и у сущностей.

## Что сознательно не входит в этот план

По `docs/planned-features.md` (актуально даже после того, как локальная персистентность перестала быть «нельзя» и стала «сделано»):

- **Сетевой слой, RTK Query, синхронизация между устройствами и совместный (семейный) доступ.** Инструмент под sync зафиксирован (`docs/planned-features.md`), но `createApi`/эндпоинты, модели участника/семьи и сама синхронизация — это следующий этап, отдельный от текущего плана. SQLite здесь строго локальная БД одного устройства, не более.
- **UUID вместо `generateId`, поля `updatedAt`/`version`/`deviceId`/`memberId`.** Нужны только для будущей синхронизации между устройствами/участниками (см. пункт выше) — не добавлять «про запас» при проектировании схемы Drizzle; текущий `generateId` как `TEXT PRIMARY KEY` подходит.
- **Конвертация валют.** Не пробел, а зафиксированное архитектурное решение приложения (`docs/app-overview.md`) — суммы/балансы всегда в валюте своего счёта, агрегаты либо в разрезе одной валюты, либо списком по валютам. Этот план его не меняет и меняться не должен.
- **Веб-платформа.** Экраны построены на нативных SwiftUI-компонентах `@expo/ui` (`Picker`, `FieldGroup`, `DatePicker` и т.п.), у которых нет реализации под web — приложение не запускается интерактивно в браузере независимо от этого плана, и это не пробел персистентности, а более широкое, уже принятое архитектурное решение (iOS-first, Liquid Glass — см. `docs/ux-guidelines.md`). Замена нативного UI на кросс-платформенный — отдельная, значительно более крупная инициатива, вне рамок этого документа.
