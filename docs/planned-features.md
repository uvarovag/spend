# Запланированные фичи и архитектурная совместимость

Документ не о том, что делать прямо сейчас, а о том, **чего не делать** в текущей разработке, чтобы не пришлось потом переписывать архитектуру ради фич, которые уже запланированы. Ни одна из фич ниже не реализуется сейчас — это чисто ограничения на дизайн новой бизнес-логики, добавляемой уже сегодня. Обновлять при уточнении деталей фич или при появлении новых пунктов роадмапа.

Смежный документ: `docs/app-overview.md` (как приложение устроено сейчас).

## Фича: синхронизация с сервером (offline-first)

Идея: главная база данных живёт **на телефоне** — приложение полностью работает офлайн, ничего не ждёт от сети. При наличии интернета происходит фоновая синхронизация локальных данных на сервер (и, видимо, обратно — между устройствами одного пользователя). Сервер — не источник истины при каждом обращении, а копия для бэкапа/шаринга между устройствами.

Что это означает для текущей архитектуры:

- **Не привязываться к тому, что `entities/*/model/use-*.ts` — это финальная реализация хранилища.** Сейчас это `createStore` поверх in-memory массива без персистентности (см. `docs/app-overview.md`) — временная заглушка. Публичный API этих файлов (`useAccounts`, `createAccount`, `updateAccount`, …) уже спроектирован как контракт, не зависящий от способа хранения — любая новая фича должна ходить только через эти функции, а не через `accountStore`/`categoryStore`/`transactionStore` напрямую (они и так не экспортируются из `entities/*/index.ts` — не начинать их экспортировать ради удобства).
- **Генерация id (`shared/lib/generate-id.ts`) — известная будущая точка миграции, не трогать превентивно.** `` `${prefix}-${Date.now()}-${Math.round(Math.random() * 1000)}` `` уникально в рамках одного процесса на одном устройстве, но не гарантированно уникально между двумя устройствами, создающими записи офлайн одновременно — при реальной синхронизации потребуется что-то вроде UUID или id с префиксом устройства. Не переделывать на UUID сейчас (YAGNI, синхронизации ещё нет) — просто не проектировать новую бизнес-логику так, чтобы она полагалась на текущий формат id (например, не парсить из id timestamp создания вместо использования поля `date`).
- **Баланс уже устроен sync-дружественно — сохранять этот принцип.** Он нигде не хранится и не кэшируется, а всегда выводится из `initialBalance + Σ транзакций` (`computeAccountBalance`) — значит два устройства, синхронизировавшие разный набор транзакций, всегда могут пересчитать согласованный баланс без отдельной логики мёржа кэша. Любая новая производная величина (агрегат, счётчик, «частая категория» и т.п.) должна точно так же **вычисляться из исходных данных на лету**, а не храниться отдельным закэшированным полем, которое пришлось бы отдельно синхронизировать и мёржить.
- Полей вроде `updatedAt`/`version`/`deviceId`, нужных для разрешения конфликтов при синхронизации, в сущностях пока нет — это ожидаемо, добавлять их сейчас не нужно. Просто не проектировать новую бизнес-логику так, чтобы отсутствие таких полей стало проблемой (например, не полагаться на порядок записей в массиве как на источник истины о том, какая версия «свежее» — для этого уже есть `date`/`id`).
- **Инструмент под этот будущий сетевой слой зафиксирован — RTK Query** (см. `AGENTS.md`, «State management: Redux Toolkit»). Это решение на будущее, а не команда начинать: пункт «Не начинать реализацию сетевого слоя» ниже продолжает действовать в полном объёме, пока фича синхронизации не запланирована к реализации отдельно.

## Фича: совместный режим ведения с семьёй

Идея: несколько человек (семья) ведут один общий учёт — счета/категории/операции общие, изменения от разных участников должны сходиться в одну картину (в связке с синхронизацией выше).

Что это означает для текущей архитектуры:

- Сейчас в приложении нет понятия пользователя/участника вообще — ни у одной сущности нет поля вроде `createdBy`/`memberId`. Это ожидаемо для однопользовательского приложения — не добавлять такие поля превентивно без реальной необходимости.
- Не проектировать новую бизнес-логику так, чтобы она **жёстко предполагала единственного локального пользователя** там, где это легко избежать — например, настройки темы/языка (`features/change-theme`, `features/change-language`) корректно живут как локальное состояние устройства (это же не общие данные семьи), а вот новая бизнес-логика, работающая с деньгами/счетами/категориями, не должна закладывать допущения вида «эти данные точно принадлежат ровно одному человеку и никогда не потребуют указания автора записи».
- Совместное редактирование означает, что два участника потенциально меняют один и тот же счёт/категорию одновременно (с разных устройств, через будущую синхронизацию) — сейчас `update*`-функции ничего не знают о конкурентных изменениях (последняя запись в массиве просто перезаписывает предыдущую). Это нормально для текущего этапа — не решать проблему конкурентности сейчас, просто не закладывать в новый код предположение, что запись в сторе гарантированно последняя актуальная версия данных.

**Кандидат-дизайн для совместного бюджета — шаринг конкретного счёта, а не полный мёрж данных семьи.** Не решение, а рассматриваемый вариант: владелец делится счётом по ссылке-приглашению и присваивает участнику отображаемое имя; операции участника на этом счёте (списание/начисление) появляются в истории владельца и актуализируют баланс счёта, но категория и заметка этих операций владельцу не видны — только сумма, тип и от кого. Привлекательность варианта — он обходит две самые тяжёлые части полного совместного режима одновременно: не требует двустороннего мёржа всей истории операций (только одностороннее «участник → владелец: вот факт операции»), и даёт приватность по умолчанию (партнёр не обязан показывать, на что именно тратит). Компромисс — это ограничивает аналитику для владельца: без категорий это контроль баланса, а не полноценная разбивка общих трат по статьям.

Что это означает для текущей архитектуры, если вариант в итоге будет выбран:

- **Не снимает зависимость от сетевого слоя выше** — участнику всё равно нужно как-то передать владельцу факт операции на общем счёте, значит это физически не может быть реализовано раньше синхронизации. Не начинать реализацию до неё.
- Понадобится лёгкая сущность «участник счёта» (id, отображаемое имя, привязка к конкретному `Account`) — не общий `User`/`Member` на всё приложение, а именно per-account. Не добавлять её сейчас.
- Баланс считается ровно как сейчас — суммой всех `Transaction` по `accountId` (`computeAccountBalance`), независимо от того, кто их создал, владелец или участник. Отдельной логики учёта участников баланс не потребует.
- Частичная видимость полей (сумма и тип видны, категория и заметка скрыты) — это фильтрация на уровне будущего протокола синхронизации, не на уровне модели данных `Transaction`: сама запись остаётся с полным набором полей, а что из неё передаётся другому участнику — решает сетевой слой. Не проектировать `Transaction` так, будто поля бывают «опциональными в зависимости от того, кто смотрит» — это вопрос прав доступа, не формы данных.
- Открытые вопросы, специально не решаем сейчас: симметрична ли видимость (участник тоже видит операции владельца в урезанном виде, или ограничение работает только в одну сторону) и что происходит с историей при разрыве шаринга. Ни один из вопросов не блокирует текущую разработку.

## Фича: регулярные операции (ипотека, подписки и т.п.)

Идея: часть операций пользователя не разовая, а повторяется с одной и той же (или почти одной и той же) суммой на регулярной основе — платёж по ипотеке, подписка на сервис, аренда, страховка. Вместо того чтобы каждый раз заводить одну и ту же операцию вручную, пользователь один раз описывает правило («Ипотека, 45 000 ₽, ежемесячно 5-го числа, счёт «Карта», категория «Жильё»»), а дальше приложение либо создаёт соответствующие операции автоматически по расписанию, либо как минимум напоминает завести их — конкретный механизм ещё не выбран.

Что это означает для текущей архитектуры:

- **Правило регулярности — не поле на Transaction, а отдельная сущность.** Transaction (`entities/transaction`) — это уже свершившийся факт с конкретными `date`/`amount` (см. `docs/app-overview.md`), а не шаблон. Регулярность («каждый месяц N-го числа», сумма, счёт, категория) со временем порождает обычные Transaction-записи, а не хранится как поле внутри них — не добавлять сейчас на Transaction поля вроде `isRecurring`/`recurrenceRule`/`parentId` «про запас».
- `computeAccountBalance` и другие производные вычисления как считали баланс суммированием реальных Transaction, так и должны продолжать — операция, порождённая правилом, физически ничем не отличается от введённой вручную (тот же набор полей), поэтому баланс не потребует отдельной логики учёта «регулярности». Ничего менять в текущих вычислениях под это не нужно.
- Категории и валютные ограничения не меняются — регулярный расход/доход это обычный `expense`/`income` с обычными `categoryId`/`accountId`, отдельного `kind` или вида категории под «регулярное» не нужно.
- Открытый вопрос на будущее, не решать сейчас: попадают ли будущие операции в Transaction заранее (тогда баланс на будущую дату уже учитывает ожидаемый платёж) или регулярная операция — это прогноз поверх реальных данных, не становящийся Transaction, пока пользователь её не подтвердит. Оба варианта совместимы с текущей моделью данных — выбор между ними откладывается до самой реализации.

## Фича: дашборд с графиками в разных разрезах за разные периоды

Идея: отдельный, более глубокий аналитический экран, чем то, что сейчас есть на Главной, — несколько типов графиков (не только текущий донат по категориям расходов), с выбором произвольного периода (не только «этот месяц») и переключением среза — по категории, по счёту, по валюте, по типу операции, динамика по времени.

Что это означает для текущей архитектуры:

- **Каждая агрегатная величина сейчас считается ad hoc, своим хуком на своём экране** (`useHomeSummary`, `useFeedItems`, `computeAccountBalance`) — напрямую от сырых `Transaction`, без общего слоя агрегации или кэша. Реализация дашборда не повод заводить единый «reporting engine» уже сейчас — этот ad hoc подход в каждом хуке (YAGNI) остаётся правильным, пока дашборд не запланирован к реализации отдельно.
- **Библиотека графиков уже выбрана и используется — `victory-native`** (`CategorySpendingDonut`, `src/pages/home/ui/category-spending-donut.tsx`). Новые типы графиков (линейные, столбчатые и т.п.) дашборд должен реализовывать через неё же, не заводить вторую чартовую библиотеку ради нового вида графика.
- **Произвольный период — уже не новая идея для этого приложения**, а расширение существующего прецедента: `useHomeSummary(currency)` и фильтры Ленты (`features/feed-filters`) уже параметризованы периодом, а не жёстко привязаны к «текущему месяцу». Дашборд лишь добавляет больше типов срезов поверх той же идеи.
- Открытый вопрос на будущее, не решать сейчас: где физически жить дашборду — отдельный таб (упирается в правило «не больше нескольких табов» из Apple HIG, уже задокументированное в `docs/ux-guidelines.md`, A6) или push-экран из Главной/Настроек, как сейчас `balance-detail`. Решение откладывается до самой реализации.

## Что делать НЕ нужно уже сейчас

Этот документ описывает ограничения на архитектуру, а не техзадание. Явно фиксируем, что не входит в текущий объём работ, пока эти фичи не запланированы к реализации:

- Не начинать реализацию сетевого слоя, авторизации, моделей пользователя/участника семьи или очереди синхронизации.
- Не начинать реализацию сущности регулярных операций (ипотека/подписки/аренда), генерации будущих Transaction по расписанию или напоминаний о них — сейчас фиксируется только сам факт, что такая фича запланирована.
- Не начинать реализацию шаринга счёта, сущности «участник счёта» или дашборда с графиками — оба зафиксированы выше только как направление и, для шаринга, как один из рассматриваемых вариантов, а не техзадание.
- Не переделывать `generateId` на UUID и не добавлять `updatedAt`/`deviceId`/`memberId` в сущности «про запас» — актуально и для схемы Drizzle ниже: `id` остаётся `TEXT PRIMARY KEY` в текущем формате, а не UUID.
- **Локальная персистентность больше не «без отдельного явного решения» — решение принято.** Стек: **expo-sqlite + Drizzle ORM**, Redux Toolkit остаётся источником истины в памяти, SQLite — write-through слой на диске. Пошаговый план — `business-logic-plan.md` в корне проекта, архитектура размещения — `AGENTS.md`, раздел «Local persistence: expo-sqlite + Drizzle ORM». Это решение — **только про локальный диск одного устройства**, оно не отменяет и не приближает ни один из пунктов выше (сеть/синхронизация/семья остаются нереализованными и незапланированными).
