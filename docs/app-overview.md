# Как устроено приложение

Справочник по текущей бизнес-логике и модели данных — читать перед реализацией любой новой бизнес-логики, чтобы новый код опирался на реальные сущности, правила и вычисления, а не дублировал/противоречил уже существующим. Обновлять при изменении сущностей, вычислений или основных пользовательских сценариев.

Смежные документы: `docs/data-constraints.md` (что нельзя менять после создания и почему), `docs/ux-guidelines.md` (визуальный язык и правило «умных» подсказок), `docs/planned-features.md` (запланированные фичи, с которыми архитектура не должна конфликтовать).

## Что это за приложение

Личный финансовый трекер: несколько счетов (в т.ч. в разных валютах), операции трёх типов (расход/доход/перевод между счетами), категории расходов/доходов, сводки на Главной и лента операций с фильтрами. Одно устройство, один пользователь, работает полностью офлайн — сейчас в приложении нет ни бэкенда, ни сети (см. `docs/planned-features.md` про то, что это временно).

## Сущности

### Account (`entities/account`)

```
{ id, name, type: 'cash'|'card'|'savings', currency, initialBalance, color, archivedAt }
```

- `currency` — один из `CURRENCY_CODES` (`RUB, USD, EUR, GBP, JPY, CNY`), фиксируется при создании навсегда (см. `docs/data-constraints.md`).
- `initialBalance` — стартовая точка отсчёта на момент создания счёта, тоже фиксируется навсегда после создания.
- `archivedAt: string | null` — мягкое удаление (ISO-дата архивации или `null`). Архивные счета не пропадают из истории операций, просто перестают быть выбираемыми для новых операций (`useAccounts()` фильтрует `archivedAt === null`; `getAccount`/`useAccount` — нет, им нужен доступ и к архивным, например чтобы отрисовать старую операцию).
- У счёта нет хранимого текущего баланса — он всегда выводится (см. «Баланс счёта» ниже).

### Category (`entities/category`)

```
{ id, name, icon, color, kind: 'expense'|'income', order, archivedAt }
```

- `kind` жёстко привязывает категорию к одному из двух типов операций — фиксируется навсегда после создания.
- `order` — ручной порядок внутри своего `kind` (drag-n-drop, `draggable-category-list.tsx` → `reorderCategories`), пересчитывается только для категорий того же `kind`.
- Как и у счёта, `archivedAt` — мягкое удаление, `useCategories(kind)` отдаёт только неархивные, отсортированные по `order`.

### Transaction (`entities/transaction`)

Дискриминированное объединение по `type`:

```
ExpenseTransaction  { id, date, note, type: 'expense',  accountId,               categoryId, amount }
IncomeTransaction   { id, date, note, type: 'income',   accountId,               categoryId, amount }
TransferTransaction { id, date, note, type: 'transfer', fromAccountId, toAccountId, fromAmount, toAmount }
```

- `date` — ISO-строка; `amount`/`fromAmount`/`toAmount` — положительные числа в валюте соответствующего счёта.
- У перевода — **две** суммы (`fromAmount`/`toAmount`), а не одна с курсом: так перевод между счетами в разных валютах не требует единого «курса» как отдельного сохранённого поля, курс просто выводится как `toAmount / fromAmount` там, где нужен для отображения (`transfer-form.tsx`).
- Никакой блокировки полей после создания на уровне типов нет (кроме теоретического ограничения на `type`, см. `docs/data-constraints.md`) — расход/доход/перевод можно полноценно редактировать через `transaction-detail-screen.tsx`, кроме привязки счёта на валюту, отличную от исходной.

## Хранилище данных (временное, in-memory)

Все три сущности живут в собственном `createStore` (`shared/lib/create-store.ts`) поверх статичного массива-затравки (`entities/*/model/mock-data.ts`), без персистентности — **при перезапуске приложения все изменения теряются**, это не база данных, а заглушка на время разработки UI. Публичный API каждой сущности — набор функций `use*`/`get*`/`create*`/`update*`/`archive*` в `model/use-*.ts`, реализующих то же самое, что делал бы будущий бэкенд-клиент (CRUD + подписка на изменения через `useStore`). Реализуя настоящую бизнес-логику (валидация, персистентность, синхронизация), сохранять эти сигнатуры функций как контракт, к которому уже привязаны все экраны — заменять реализацию внутри, а не переписывать вызывающий код.

**Зафиксировано решение по стеку (по шагам — `business-logic-plan.md` в корне проекта):**

- Этот `createStore`/`useStore` будет заменён на **Redux Toolkit** — в памяти, с сохранением контракта функций `use*`/`create*`/`update*`/`archive*` (кроме одного намеренного изменения — см. ниже).
- Поверх Redux добавляется настоящая персистентность на устройстве: **expo-sqlite + Drizzle ORM**. Redux остаётся источником истины для UI, SQLite — write-through слоем на диске: гидрация Redux из БД при старте приложения, каждая мутация пишется в Redux синхронно и в SQLite асинхронно в фоне. Из-за этого `create*`/`update*`/`archive*`-функции сущностей неизбежно становятся `async` — единственное осознанное отступление от «сохранять сигнатуры без изменений» выше.
- `entities/*/model/mock-data.ts` перестаёт быть стартовыми данными приложения — это дев-фикстуры для сидирования пустой БД в `__DEV__`; настоящее приложение стартует с нуля (0 счетов/категорий/операций).
- **RTK Query** зарезервирован под будущий сетевой/sync-слой (см. `docs/planned-features.md`) — реализация сети сейчас не начинается, это только фиксация выбора инструмента на будущее.

Подробности размещения стора и БД относительно слоёв FSD — в `AGENTS.md`, разделы «State management: Redux Toolkit» и «Local persistence: expo-sqlite + Drizzle ORM».

## Баланс счёта и денежные вычисления

Баланс счёта **не хранится**, а выводится каждый раз заново: `computeAccountBalance(transactions, accountId, initialBalance)` (`entities/transaction/model/compute-account-balance.ts`) проходит по всем операциям и суммирует расходы/доходы/переводы этого счёта поверх `initialBalance`. Так как нет закэшированного значения, любое количество правок истории (кроме заблокированных полей) никогда не может «разойтись» с реальным балансом — это и есть причина, почему поля типа `amount`/`date` у операции свободно редактируемы (см. `docs/data-constraints.md`, «Общий принцип»).

**Конвертации валют нет нигде в приложении.** Следствия, которые нужно держать в голове при любой новой денежной фиче:

- Сумма/баланс счёта всегда в его собственной валюте — нельзя складывать суммы разных счетов напрямую.
- Агрегаты, которые естественно объединяют несколько счетов (Главная, лента), либо считаются **в разрезе одной выбранной валюты** (`useHomeSummary(currency)` — фильтрует счета по валюте перед суммированием), либо возвращают **список сумм по каждой валюте отдельно** (`useFeedItems` → `CurrencyTotal[]`, показывается как несколько чипов).
- Перевод между счетами в разных валютах хранит обе введённые пользователем суммы как факт (никакого «истинного» курса ЦБ) — курс на экране лишь производный от них.
- Форматирование денег — всегда через `formatCurrency`/`currencySymbol` (`shared/lib/format-currency.ts`): максимум 2 знака после запятой без хвостовых нулей, символ через `Intl.NumberFormat` с ручным фолбэком на частые валюты (Hermes не всегда знает узкий символ).

## «Умные» дефолты при вводе операции

Подробное правило — `docs/ux-guidelines.md`, раздел I. Коротко: при вводе/редактировании операции (не в фильтрах, не в администрировании счетов/категорий) подсказывается наиболее вероятный выбор по истории — частые категории за 30 дней (`useFrequentCategories`), последний использованный счёт (`useLastUsedAccountId`), самая частая пара счетов для перевода за 30 дней (`findMostFrequentTransferPair`), а полный список счетов в `pick-account` сортируется по давности использования счёта именно в роли списания/зачисления (`sortAccountsByRole`). Любая новая денежная фича с похожим выбором (счёт/категория/получатель) должна следовать этому же принципу, а не изобретать своё.

## Экраны и сценарии

- **Онбординг** (`pages/onboarding`) — на него Главная (`pages/home`) редиректит (`<Redirect href="/onboarding" />`), пока не установлен персистентный флаг `onboarding-completed` (`features/onboarding`, `expo-sqlite/kv-store`, тот же паттерн write-through персистентности настроек, что и у темы/языка). Показывается только для по-настоящему нового пользователя: редирект срабатывает, если флаг не установлен **и** ещё нет ни одного счёта — если счета уже есть (например, dev-сид или обновление с версии до онбординга), Главная сама молча помечает флаг завершённым, не показывая экран. Дальше флаг не сбрасывается никогда, даже если счета/категории потом удалить. Степпер на 3 шага внутри одного экрана (без пуша отдельных роутов): 1) короткое текстовое приветствие (единственный по-настоящему кастомный шаг — реюзать для него нечего), 2) `AccountFormFields`, 3) `CategoryFormFields` (`kind="expense"`, т.к. в самой форме нет переключателя типа — как и в оригинальном `category-form`). Это ровно то же тело формы, что рендерят `pages/accounts/ui/account-form-screen.tsx`/`pages/categories/ui/category-form-screen.tsx` в своих модалках — вынесено в `features/account-form`/`features/category-form`, чтобы не поддерживать два места с одинаковыми полями; сама модалка оставляет себе только шапку (`ModalHeader`) и `onSaved={() => router.back()}`, онбординг — `onSaved={() => setStep(step + 1)}`. «Skip» в шапке и естественное завершение (после сохранения категории) делают одно и то же — ставят флаг и уводят на Главную.
- **Главная** (`pages/home`) — сводка по одной выбранной валюте (переключатель вверху, если валют несколько): баланс, расход/доход за месяц, разбивка расходов по категориям (донат-чарт), последние операции, кнопки быстрого ввода расхода/дохода/перевода.
- **Лента** (`pages/feed`) — полный список операций, сгруппированный по дате, с фильтрами (тип/категория/счёт/период — `feature/feed-filters`) и суммами по валютам сверху.
- **Настройки** (`pages/settings`) → **Счета**/**Категории** — списки с созданием/архивацией/редактированием (для категорий — ещё и drag-n-drop сортировка), плюс тема и язык интерфейса.
- **Добавление операции** (`pages/add-transaction`, модалка) — единственная точка входа: три кнопки на Главной передают `type` параметром навигации; тип операции **не переключается** внутри уже открытого экрана (см. `docs/ux-guidelines.md`, F).
- **Детали операции** (`pages/transaction-detail`, модалка) — просмотр/редактирование/удаление существующей операции, та же форма, что и при создании, без переключателя типа.
- **pick-account / pick-category** — вспомогательные модальные экраны выбора, пушатся поверх уже открытой модалки без второго слоя `presentation: 'modal'` (см. `docs/ux-guidelines.md`, A1/A4).

## Локализация и тема

- Язык — `i18next` + `react-i18next`, ресурсы `shared/i18n/locales/{en,ru}.json`, по умолчанию берётся язык устройства (`detectDeviceLanguage`, поддержаны только `en`/`ru`, иначе фолбэк на `en`); переключается вручную в Настройках и хранится в `createValueStore`.
- Тема — `system`/`light`/`dark` через `nativewind`'s `colorScheme.set` (`features/change-theme`), `system` следует настройке ОС.
