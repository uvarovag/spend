# UX-правила проекта (Apple HIG)

Свод конкретных, проверяемых правил интерфейса — не только модалки и кнопки, а весь язык дизайна приложения: типографика, цвет, навигация, списки, поля ввода, тексты. Основано на актуальных страницах Apple Human Interface Guidelines (декабрь 2025 / март–июнь 2026) — приложение iOS-первое, использует Liquid Glass (`expo-glass-effect`), нативные табы (`expo-router/unstable-native-tabs`) и нативные `@expo/ui` контролы. Каждое правило по возможности привязано к конкретному файлу/компоненту — либо как «уже так, сохранять», либо как открытый вопрос/техдолг. Обновлять при появлении новых типов экранов и компонентов.

## A. Модалки и навигация

### A1. Модалка — это одна узкая задача, а не отдельное приложение

- Одна модалка = одна простая, короткая, законченная задача. Если задача разрослась — это повод разбить её или вынести в полноэкранный modal, а не плодить вложенность.
- Внутри модалки — один путь без вложенной иерархии экранов. Не должно быть кнопок, которые можно спутать с закрытием модалки.
- **Открыта может быть только одна модалка одновременно.** Если действие внутри модалки должно открыть ещё один выбор — это шаг того же сценария (см. A4: пуш внутри текущей шторки + «Назад»), а не новая модалка поверх текущей.
  - **Исправлено:** `CategoryPicker` (`src/features/add-transaction/ui/category-picker.tsx`) делает `router.push('/pick-category', …)` изнутри `add-transaction`/`transaction-detail`. Раньше `pick-category` был объявлен с `presentation: 'modal'` в `src/app/_layout.tsx`, из-за чего получалась модалка поверх модалки. Теперь у `pick-category` нет `presentation: 'modal'` — это обычный пуш внутри уже открытой шторки (тот же грабер/скругления/фон, без второго слоя), а его шапка показывает «Назад» вместо «Закрыть».

### A2. Кнопка закрытия («Закрыть» / Close)

- Всегда есть, всегда на левом (leading) краю шапки, всегда один и тот же способ выйти без обязательного сохранения.
- В проекте — текстовая кнопка (`ModalHeader`, `src/shared/ui/modal-header.tsx`), не иконка. Это осознанный выбор одного паттерна на всё приложение — придерживаться его everywhere, не смешивать с крестиком-иконкой на одних экранах и текстом на других.
- **Никогда не показывать одновременно три кнопки** «Закрыть/Отмена» + «Назад» + «Готово» — прямое указание Apple HIG (Sheets): выбирать максимум две из трёх на экран.
- Если закрытие может стереть введённые пользователем данные — по HIG должно быть подтверждение (алерт/action sheet) перед закрытием. **Сейчас в проекте это нигде не реализовано** (закрытие всегда мгновенное) — открытый вопрос на будущее, внедрять по решению, не по умолчанию.
- `ModalHeader` также принимает `rightAction` (правый слот шапки), но сейчас его никто не передаёт — фильтры Ленты (`feed-filters-screen.tsx`), где раньше был такой сценарий («Сбросить» слева / «Готово» справа), переехали на нативный `@expo/ui`-список (`FieldGroup`/`ListItem`) с обычным «Закрыть» в шапке, а «Готово»/«Сбросить» — в стандартном нижнем блоке кнопок (см. H). Не добавлять `rightAction` ради симметрии — если он понадобится, значит появился новый сценарий, а не потому что проп уже есть.

### A3. Главное действие — всегда одна крупная кнопка

- На экране не больше 1–2 «акцентных» (ярких, залитых цветом) кнопок. Если действий-кандидатов больше — только самое вероятное получает акцент, остальные — нейтральный/приглушённый стиль.
- Главная кнопка — крупная, на всю ширину, в зоне, удобной большому пальцу (низ экрана), с хит-зоной не меньше 44×44pt (минимум Apple HIG). В проекте это `GlassButton` (`src/shared/ui/glass-button.tsx`), закреплённый снизу поверх прокручиваемого контента (`account-form`, `category-form`, `transaction-detail`, `add-transaction`) — паттерн уже соответствует правилу, использовать его для любого нового экрана с основным действием. **Важно:** сохранение/добавление — это всегда главное действие экрана, даже если по смыслу это «просто закрыть модалку» (как в `add-transaction`, где раньше сабмит был текстовой кнопкой в шапке справа — перенесён в `GlassButton` внизу, чтобы не выбиваться из правила).
- Apple HIG (Layout) отдельно предупреждает: full-width кнопка на iOS должна быть отступлена от самого края экрана, а не буквально край-в-край. У нас так и есть — плавающий контейнер с кнопками всегда с `px-4` (`account-form-screen.tsx`, `category-form-screen.tsx`, `transaction-detail-screen.tsx`, `add-transaction-screen.tsx`), сама кнопка растягивается только внутри этого отступа.
- **Деструктивное действие (архивировать/удалить) никогда не делается «главной»/акцентной кнопкой**, даже если пользователь чаще всего нажимает именно её. В проекте — единый стиль для любого деструктивного действия: плоская текстовая ссылка без фона, красным текстом (`accounts.archive`/`categories.archive`/`transactionDetail.delete`), без стеклянного фона — минимальная визуальная масса относительно главной кнопки. `GlassButton` больше не имеет `variant` — он всегда акцентный/главный; деструктив всегда обычный `Pressable` + `Text`.
- **Любое необратимое действие подтверждается алертом перед выполнением, а не срабатывает по одному тапу.** Архивация счёта/категории и удаление операции необратимы (см. `docs/data-constraints.md`, `docs/app-overview.md`) — нажатие на деструктивную ссылку (предыдущий пункт) открывает `Alert.alert(title, message, [Cancel, Destructive])` из `react-native` и только по тапу на деструктивную кнопку алерта выполняет само действие. Один и тот же паттерн уже реализован трижды: `handleArchive` в `src/features/account-form/ui/account-form-fields.tsx`, `handleArchive` в `src/features/category-form/ui/category-form-fields.tsx`, `handleDelete` в `src/pages/transaction-detail/ui/transaction-detail-screen.tsx` — использовать его как образец для любого нового необратимого действия, а не изобретать свой:

  ```tsx
  Alert.alert(t('accounts.archiveConfirmTitle'), t('accounts.archiveConfirmMessage'), [
    { text: t('common.cancel'), style: 'cancel' },
    {
      text: t('accounts.archive'),
      style: 'destructive',
      onPress: () => {
        void archiveAccount(existingAccount.id);
        onArchived?.();
      },
    },
  ]);
  ```

  Заголовок — короткий вопрос («Архивировать счёт?», «Удалить операцию?»), сообщение заканчивается фразой о необратимости («Это действие необратимо.» / «This can't be undone.») — ключи `*.archiveConfirmTitle`/`*.archiveConfirmMessage` (`categories`/`accounts`) и `transactionDetail.deleteConfirmTitle`/`deleteConfirmMessage` в `shared/i18n/locales/{en,ru}.json`. Кнопка отмены — `style: 'cancel'` (`common.cancel`), кнопка подтверждения — `style: 'destructive'` с той же подписью, что и исходная деструктивная ссылка на экране (`accounts.archive`/`categories.archive`/`transactionDetail.delete`), не отдельная строка «Да»/«Confirm». Это не то же самое, что открытый вопрос в A2 (подтверждение при закрытии модалки со несохранёнными данными) — там решение пока не принято и не реализовано, здесь же для архивации/удаления это уже сделанное и обязательное правило.

  **Правило для текста сообщения (не только заголовка): описывать реальное, конкретное последствие действия, а не общую формулировку.** Заголовок — это вопрос («Архивировать...?»), а тело сообщения обязано ответить пользователю «и что конкретно после этого изменится» — без этого подтверждение неинформативно и его подписывают не глядя. Если действие меняет не всё, а только часть — сообщение обязано разграничить, что именно изменится, а что нет, а не обобщать до «пропадёт отовсюду». **Исправлено:** `accounts.archiveConfirmMessage`/`categories.archiveConfirmMessage` раньше гласили «Счёт/категория исчезнет из всех списков» — неверно: `archivedAt` (см. `docs/data-constraints.md`) это мягкое скрытие только из списков *выбора* (`useAccounts()`/`useCategories()` фильтруют `archivedAt === null`) — из уже добавленных операций счёт/категория никуда не пропадает (`getAccount`/`getCategory`/`useAccount`/`useCategory` по id архивные не фильтруют, см. `docs/app-overview.md`), в Ленте и в деталях операции всё выглядит как раньше. Формулировка переписана на «Пропадёт из списков выбора и из Настроек, но останется как есть в уже добавленных операциях» — называет и что меняется, и что нет, вместо неточного «везде». `transactionDetail.deleteConfirmMessage` этой правки не требует: удаление операции — не мягкое скрытие, а фактическое удаление записи, там нечего разграничивать, обобщённая формулировка тут не искажает факт. Если для нового необратимого действия эффект будет частичным/выборочным (как у архивации) — писать сообщение по этому же принципу, а не копировать первую попавшуюся формулировку.
- Подпись кнопки — короткий глагол в повелительном наклонении («Сохранить», «Удалить», «Готово», «Архивировать») — уже так во всех локалях, сохранять этот стиль для новых кнопок.
- Компактная круглая иконка-кнопка (например кнопка фильтров в `feed-screen.tsx`, левый верхний угол) — `GlassIconButton` (`src/shared/ui/glass-icon-button.tsx`), тот же GlassView/BlurView-паттерн с нейтральным `tintColor` (см. следующий пункт), плюс опциональный `active`-индикатор (точка) для «есть применённые фильтры».
- **Важно, и это общее правило для любого нового компонента на `GlassView`:** обязателен нейтральный `tintColor`. «regular» Liquid Glass без тона почти не виден на сплошном фоне (эффект держится на краях, а не на плоской заливке) — так было изначально у `GlassIconButton` (кнопка фильтров в `feed-screen.tsx` буквально сливалась с белым фоном, пока не добавили тон), без тона элемент выглядит как будто его нет.
- **Отдельное правило для нативных контролов:** не оборачивать в `GlassView`/`BlurView`-капсулу нативный контрол, у которого УЖЕ есть собственный фон/капсула — получается капсула внутри капсулы, два вложенных скруглённых слоя выглядят хуже, чем один нативный. Такой контрол просто кладётся в `Host` как есть, без обёртки. Сейчас в проекте нет ни одного `@expo/ui` контрола, к которому это применимо (дата — см. следующий пункт, — больше не нативная), но правило остаётся в силе на будущее, если такой контрол снова появится.
- **Исправлено:** выбор счёта в `add-transaction` (расход/доход) раньше был компактным чипом (`GlassChip`) рядом с датой в одну строку — из-за неоднородности со стилем перевода и невозможности показать баланс счёта. Теперь оба сценария используют одну и ту же карточку счёта `AccountCard` (`src/entities/account/ui/account-card.tsx` — иконка, название, баланс, шеврон). `GlassChip` как компонент удалён — больше не используется ни на одном экране.
- **Исправлено:** дата (`add-transaction`/`transaction-detail`/`transfer`) раньше была нативным `DatePicker` (`@expo/ui/swift-ui`, `datePickerStyle('compact')`) — заменена на кастомный `DateCard` (`src/shared/ui/date-card.tsx`, обычные RN-компоненты, без `Host`/native module), по форме и поведению — точная копия `AccountCard`: иконка в кружке, текущая дата («Сегодня»/«Вчера» вместо числа, если применимо), подпись «Date»/«Дата» под ней, шеврон. Тап открывает `pick-date` — новый экран того же типа, что `pick-account`/`pick-category` (пуш поверх уже открытой модалки, `closeLabel={t('common.back')}`, без своего `presentation: 'modal'` — см. A1/A4): чипы «Сегодня»/«Вчера» (`common.today`/`common.yesterday`) и сетка календаря на месяц (понедельник первым, навигация по месяцам стрелками). Результат возвращается через `shared/lib/picked-date-store.ts` — тот же паттерн, что `picked-account-store.ts`/`picked-category-store.ts`, только в `shared`, а не в `entities`/`features`, потому что дата не принадлежит одной сущности и нужна и `features/add-transaction`, и `features/transfer`. `DateCard`, в отличие от `AccountCard`, сам владеет навигацией и обработкой результата (не оставляет это вызывающей стороне) — у даты нет вариаций по ролям (`from`/`to` и т.п.), которые оправдывали бы разбивку.

### A4. «Назад» vs «Закрыть» — разные вещи, не путать

- **Назад** — переход на шаг назад внутри одного и того же многошагового сценария (мастер, wizard). Не закрывает модалку целиком, а возвращает к предыдущему шагу той же задачи. Показывается только если предыдущий шаг есть.
- **Закрыть/Отмена** — выход из модалки целиком, к тому экрану, откуда её открыли.
- На одном экране в шапке — либо «Закрыть» (первый/единственный шаг), либо «Назад» (не первый шаг одного сценария), но не оба сразу.
- Реализовано: `ModalHeader` (`src/shared/ui/modal-header.tsx`) принимает `closeLabel` — по умолчанию `common.close` («Закрыть»), но экран, до которого можно дойти только пушем из другого модального экрана (сейчас — `pick-category`, `src/pages/pick-category/ui/category-list-screen.tsx`), передаёт `closeLabel={t('common.back')}` («Назад»). Обработчик (`onClose`/`router.back()`) один и тот же — меняется только подпись, отражающая реальный смысл действия для конкретного экрана.
- При добавлении нового шага в существующий сценарий (а не новой независимой модалки) — тот же приём: пуш без `presentation: 'modal'` + `closeLabel={t('common.back')}` на всех шагах, кроме первого.

### A5. Хит-зоны и обратная связь на нажатие

- Любой интерактивный элемент — минимум 44×44pt зоны нажатия (Apple HIG), даже если визуально он меньше. Для текстовых/иконных кнопок меньшего размера — добавлять `hitSlop` (уже сделано для «Закрыть»/«Назад» в `ModalHeader`, «Готово» у заметки в `note-field.tsx`, кнопок «+» в `account-list-screen.tsx`/`category-manage-screen.tsx`).
- У каждой кастомной нажимаемой зоны должно быть заметное состояние нажатия (иначе кажется, что кнопка не реагирует). В проекте — `active:opacity-70` / `active:opacity-80`, использовать этот же приём для новых `Pressable`.
- Disabled-состояние интерактивного элемента — приглушение до `opacity: 0.4`/`opacity-40`, единое значение на всё приложение. Уже так в `GlassButton` (`shared/ui/glass-button.tsx`, `opacity: disabled ? 0.4 : 1` — главная кнопка на `account-form`/`category-form`/`add-transaction`/`transaction-detail`/`feed-filters`) и в кнопке «Архивировать» (`account-form-fields.tsx`, `opacity-40`, пока у счёта не нулевой баланс — см. `docs/data-constraints.md`). Само по себе приглушение — не единственная обратная связь: рядом всегда текст, поясняющий, почему действие недоступно (`accounts.archiveBlockedByBalance`) — не оставлять disabled-элемент без объяснения (см. E про валидацию полей — тот же принцип).

### A6. Табы — навигация, не действия

- Таб-бар (`src/app/(tabs)/_layout.tsx`) — только для переключения между верхнеуровневыми разделами (Обзор/Лента/Настройки). Для действий над текущим экраном — кнопки в шапке/внизу экрана, не таб.
- Уже соответствует HIG: 3 таба (в пределах разумного, HIG предупреждает от лишних), однословные подписи (`t('tabs.home')` и т.п.), иконки — через SF Symbols нативно (`<NativeTabs.Trigger.Icon sf="chart.pie" />`), что даёт настоящий Liquid Glass таб-бар и автоматическую адаптацию — именно то, что рекомендует HIG вместо кастомных иконок.
- Не прятать и не делать disabled таб-кнопки, даже если раздел временно пуст — показывать пустое состояние (`empty` тексты уже есть в `feed`/`home`) внутри вкладки, а не убирать саму вкладку.
- Таб-бар может быть перекрыт только модалкой (наш случай — все экраны из `presentation: 'modal'` перекрывают его) — единственное исключение, которое допускает HIG.

## B. Типографика

- Не использовать лёгкие/тонкие начертания (Ultralight/Thin/Light) — только Regular/Medium/Semibold/Bold, иначе текст плохо читается в мелких размерах. Уже так во всём проекте (`font-medium`/`font-semibold`/`font-bold`; `font-thin`/`font-light`/`font-extralight` в коде не встречаются) — сохранять при добавлении новых текстов.
- Не отключать системное масштабирование текста (Dynamic Type/`allowFontScaling`). Нигде в проекте `allowFontScaling={false}` не выставлен — не добавлять его ради «более предсказуемой» вёрстки, вместо этого проектировать строки так, чтобы они переживали больший шрифт (см. пункт про списки).
- Самая важная информация в строке — не должна ужиматься/скрываться первой при росте шрифта; второстепенная (подпись, дата, счёт) — может. У нас это уже выражено размером (`text-base` для главной строки, `text-xs` для вторичной) — сохранять эту иерархию для новых строк, а не делать всё одним размером.
- Минимизировать число разных текстовых стилей на одном экране — держаться уже заданного набора (`text-xs`/`text-sm`/`text-base`/`text-lg`/`text-3xl` + `font-medium`/`semibold`/`bold`), не вводить произвольные размеры под конкретный экран.

## C. Цвет

- Один цвет — одно устойчивое значение по всему приложению, не переиспользовать для разных смыслов. Уже так: красный = расход/деструктивное действие, зелёный = доход, синий = основное интерактивное действие/ссылка/выбранное состояние. Не красить что-то ещё в красный/зелёный «просто для акцента» — это будет читаться как расход/доход. Красный переиспользован и для баннера ошибки записи в БД (`shared/ui/error-banner.tsx`, `business-logic-plan.md`, Шаг 14) — это не новый смысл, а тот же «что-то пошло не так/требует внимания», под который красный уже отведён.
- Каждый кастомный цвет — с осмысленным тёмным вариантом, а не одним и тем же значением в обеих темах. В NativeWind это `dark:`-вариант класса — уже используется почти везде (`text-neutral-900 dark:text-neutral-50` и т.п.); для новых экранов не забывать про `dark:`, не полагаться на то, что светлая палитра «и так сойдёт».
- Цвет — не единственный носитель смысла (доступность для людей с цветовой слепотой). У нас так и есть: выбранная категория отмечена не только другим фоном, но и отдельным чек-бейджем (`CategoryTile`), а не одним лишь изменением цвета — сохранять этот приём, а не заменять его чисто цветовой подсветкой.
- В Liquid Glass — красить только то, что реально требует акцента (главное действие), и красить именно фон элемента (`tintColor` у `GlassView`/`GlassButton`), а не текст/иконку поверх стекла — так и сделано.

## D. Списки

- Короткий, читаемый текст в строке; вторичная информация — отдельной, более блёклой строкой ниже (уже паттерн `TransactionRow`, `account-list-screen.tsx`, `draggable-category-list.tsx`).
- **Исправлено:** строки с пользовательским текстом переменной длины (название категории/счёта, «откуда → куда» в переводах, сумма) — были без `numberOfLines`, из-за чего при длинном названии или увеличенном системном шрифте текст мог перенестись и сломать высоту строки списка. Добавлен `numberOfLines={1}` во всех основных Text-строках `TransactionRow` (`src/widgets/transaction-row/ui/transaction-row.tsx`), `account-list-screen.tsx` и `draggable-category-list.tsx`. При добавлении новой строки списка с пользовательским текстом — сразу закладывать `numberOfLines={1}`, не только на вторичной подписи.
- Явная обратная связь при нажатии на строку — press-state есть везде (`active:opacity-70`); для reorder-списка категорий — визуальный drag-предпросмотр (`draggable-category-list.tsx`).

## E. Текстовые поля и ввод

- Использовать клавиатуру, подходящую под тип данных: числовой ввод — `keyboardType="decimal-pad"`. Уже так для суммы начального баланса (`account-form-screen.tsx`) — сохранять для любых новых числовых полей, не оставлять их на дефолтной клавиатуре.
- Плейсхолдер — не единственный способ объяснить назначение поля: как только пользователь начал печатать, подсказка исчезает, и в форме без отдельной подписи становится непонятно, что это было за поле. **Открытый вопрос:** сейчас поля `Name` (оба экрана) и `Initial balance` (`account-form-screen.tsx`, только при создании) — только плейсхолдер, без постоянной подписи над полем (в отличие от `Color`-секции на обоих экранах и `Icon`-секции на `category-form-screen.tsx` — у счёта отдельного поля иконки нет, иконка выводится из `type`, — у которых подпись есть). HIG рекомендует такую подпись добавлять; решение — за пользователем, т.к. меняет плотность формы, не исправлять тихой правкой.
- Валидировать поля и явно показывать ошибку рядом с полем, а не молча ничего не делать. **Исправлено:** `account-form-screen.tsx` и `category-form-screen.tsx` — `handleSave` при пустом имени вместо молчаливого `return` выставляет `nameError`, отображаемый как `text-xs text-[#FF3B30]` под полем (`accounts.nameRequired`/`categories.nameRequired` — «Enter a name»/«Введите название»), и сбрасывает его при следующем вводе. Формы `add-transaction`/`transaction-detail` (сумма/счёт/категория) не тронуты этой правкой — там кнопка «Готово» и так управляется через `disabled={!canSubmit}` (`add-transaction-screen.tsx`), так что тапнуть по невалидной форме физически нельзя и молчаливого отказа там нет — сообщение об ошибке добавило бы код на недостижимый сценарий.
- **Однострочный `TextInput` — всегда фиксированная высота (единая `h-12` для любого однострочного поля ввода данных операции), никогда `py-*`; размер шрифта — произвольным значением (`text-[16px]`), никогда именованным классом (`text-base`/`text-lg`).** Причина — не стилистическая, а платформенная: у однострочного `TextInput` на iOS реальная высота поля не подстраивается под `line-height`, который несёт с собой именованный Tailwind-класс (`text-base` = `font-size:16 + line-height:24`), а вычисляется отдельно, по натуральным метрикам шрифта. Из-за этого расхождения высота поля пересчитывается заново на каждое изменение текста (видно как «прыжки» высоты при вводе), а сам текст оказывается смещён относительно плейсхолдера/центра поля (текст и плейсхолдер в норме используют один и тот же стиль, но расходятся, если этот стиль внутренне противоречив). `text-[16px]` (в отличие от `text-base`) не тянет за собой `line-height` — тогда используется натуральное значение, то же самое, что и для высоты поля, и обе величины перестают расходиться. **Исправлено** во всех однострочных полях ввода: `Name` (`account-form-fields.tsx`, `category-form-fields.tsx`), `Initial balance` (`account-form-fields.tsx`), сумма перевода (`transfer-form.tsx`) — везде `h-12` + `text-[16px]`, включая соседние нередактируемые элементы той же строки (блок валюты, статичный текст суммы в режиме редактирования), чтобы строка не теряла общую высоту при переключении между созданием и редактированием. **Не касается `multiline`-полей** (`note-field.tsx`) — там RN использует другой рендер-путь (`UITextView`/TextKit), у которого нет этого расхождения, поэтому `text-sm`/`text-base` там сами по себе не ломаются; `note-field.tsx` тем не менее переведён на `text-[16px]` вместе с остальными полями — не из-за бага, а чтобы у всех полей ввода данных операции (а не подписей/лейблов) был один размер шрифта.

## F. Сегментированные переключатели

- Не больше 5 сегментов на iPhone. Уже так: общий `SegmentedSwitcher` (`src/shared/ui/segmented-switcher.tsx`) используется для типа счёта (Cash/Card/Savings — 3 сегмента, `account-form-screen.tsx`) и типа категории (Expense/Income — 2 сегмента, `category-manage-screen.tsx`).
- Только текст ИЛИ только иконки в одном контроле, не вперемешку — у нас везде только текст — сохранять, не добавлять иконки в один из сегментов выборочно.
- `SegmentedSwitcher` (`src/shared/ui/segmented-switcher.tsx`) — нативный `Picker` с `pickerStyle('segmented')` из `@expo/ui/swift-ui` (резолвится и как web-фолбэк). Приложение iOS-first и не поддерживает Android — платформенных вариантов этого компонента нет.
- Использовать для переключения состояния/подвида одного и того же объекта (тип операции, тип счёта), а не для навигации между независимыми разделами приложения — это уже разведено правильно: разделы приложения = табы (A6), состояние формы = сегменты.
- **Исправлено:** раньше под каждый такой выбор был свой компонент (`TypeSwitcher`, `AccountTypeSwitcher`, `KindSwitcher`) с побайтово одинаковой разметкой — сведены в один `SegmentedSwitcher<T>`, параметризованный списком опций и функцией подписи. Отдельно: тип операции (расход/доход/перевод) в `add-transaction` раньше можно было переключить сегментированным контролом прямо внутри уже открытого экрана — теперь это не состояние формы, а точка входа: тип приходит только параметром навигации от кнопки на Главном (`quick-actions.tsx`) и не может быть изменён, пока экран открыт.

## G. Текст в интерфейсе (Writing)

- Подпись кнопки — глагол, коротко, по делу («Сохранить», «Готово», «Удалить»), не «творческие» формулировки — уже так, сохранять при добавлении новых кнопок.
- В сообщениях об ошибках не начинать с «Мы»/«We» — по HIG это создаёт неясность, кто это «мы»; писать по факту («Не удалось загрузить», а не «У нас не получилось загрузить»). Уже так у обоих существующих сообщений об ошибках: `nameError` в формах счёта/категории (п. E — «Введите название»/«Enter a name») и баннер сбоя фоновой записи в SQLite (`shared/ui/error-banner.tsx`, `errors.saveFailed` — «Не удалось сохранить изменения на устройстве») — оба по факту, без «мы». Придерживаться того же тона для любых новых сообщений.
- Не использовать «ой!»/«упс!» и подобные интерфейсные восклицания — звучит несерьёзно для финансового приложения, где важнее ощущение надёжности, чем игривости.
- Единый регистр по типу элемента, не по экрану: кнопки — с заглавной первое слово (RU: «Сохранить», «Готово»; EN: Title Case — «Save», «Done»), плейсхолдеры/описания — обычным предложением («Добавить заметку») — уже так, сохранять при добавлении новых строк локализации.

## H. Отступы и интервалы (Spacing)

Единая шкала интервалов (кратна 4pt) — для одинаковой по смыслу связи между элементами использовать один и тот же шаг во всех компонентах и экранах, а не подбирать число под конкретный экран.

- **`px-4` (16pt) — горизонтальный отступ от края экрана.** Универсально для любого контента впритык к краю: шапка (`ModalHeader`), строки списков, плавающие кнопки внизу, обёртки форм. Самый частый класс в проекте — исключений нет, сохранять для любого нового экрана.
- **`gap-2` (8pt) — подпись сверху, содержимое снизу.** Между `Text`-лейблом секции и тем, что он описывает: `ColorSwatchPicker`/сетка иконок под подписью «Цвет»/«Иконка» (`account-form-screen.tsx`, `category-form-screen.tsx`), заголовок «Расходы по категориям»/«Последние операции» над содержимым (`home-screen.tsx`). Тот же шаг переиспользован для сетки кнопок цифровой клавиатуры (`numeric-keypad.tsx`) — другой по смыслу случай, но совпадение значения ничему не противоречит.
- **`gap-3` (12pt) — иконка/аватар и текст в строке.** Между круглой иконкой счёта/категории и текстовым блоком: `AccountCard`, `DateCard`, `TransactionRow`, строки `account-list-screen.tsx`/`pick-account-screen.tsx`/`draggable-category-list.tsx`, а также между двумя соседними карточками статистики (`StatCard` × 2 в `home-screen.tsx`). **Исключение:** высота строки в `draggable-category-list.tsx` зафиксирована константой `rowHeight = 64` (нужна для математики drag-n-drop), внутренний `Pressable` использует `py-2` вместо стандартного `py-3` из следующего пункта — это не влияет на видимую высоту строки (она уже задана через `style={{ height: rowHeight }}`), поэтому не переносить сюда `py-3` по аналогии с обычными списками.
- **`py-3` (12pt) — вертикальный паддинг нажимаемой строки без фиксированной высоты.** Строки списка и деструктивные текстовые ссылки («Архивировать»/«Удалить»): `account-list-screen.tsx`, `pick-account-screen.tsx`, `TransactionRow`, `AccountCard`, `DateCard`, кнопка «Все» в `category-picker.tsx`.
- **`gap-4` / `pt-4` (16pt) — отступ между смысловыми секциями экрана.** Единый шаг вертикального ритма для любой прокручиваемой страницы — между `CategoryPicker`/`AccountDateSection`/`NoteField` (`add-transaction-screen.tsx`, `transaction-detail-screen.tsx`), между группой карточек счетов и суммой в `transfer-form.tsx`, между блоками формы счёта/категории (`account-form-screen.tsx`, `category-form-screen.tsx`) и между секциями Главной (`home-screen.tsx`). **Исправлено:** формы счёта/категории раньше использовали `gap-6` (24pt), Главная — `gap-5` (20pt) — три разных значения для одной и той же роли; приведено к одному `gap-4`.
- **`pb-40` — отступ снизу контента `ScrollView`.** На любом экране с плавающей кнопкой внизу (`GlassButton`), чтобы последний элемент списка/формы не перекрывался кнопкой или клавиатурой. Уже так везде, где есть плавающая кнопка — сохранять для новых экранов такого типа.
- **`px-4 pb-4 pt-2` (+ `gap-1`, если кнопок две) — плавающий блок с кнопками внизу экрана.** Единый паттерн «главная кнопка + деструктивная ссылка под ней»: `account-form-screen.tsx`, `category-form-screen.tsx`, `add-transaction-screen.tsx`, `transaction-detail-screen.tsx`, `feed-filters-screen.tsx`. Уже так везде — не менять форму этого блока при добавлении новых экранов с главным действием внизу.

**Не подпадает под это правило — внутренний паддинг самого компонента, а не отступ между соседними элементами:** размер кнопки (`GlassButton` — `py-4`, кнопки клавиатуры в `numeric-keypad.tsx` — `py-5`), высота шапки (`ModalHeader` — `pt-6 pb-6`), внутренние отступы `NoteField`/`AmountInput`, компоновка легенды `category-spending-donut.tsx`. Эти значения настроены под конкретный визуальный элемент — подбирать их под сам элемент, а не под шкалу выше.

**Зависит от системного окружения экрана, не унифицировать бездумно:** нижний отступ прокручиваемого списка без плавающей кнопки — `pb-24` в `account-list-screen.tsx`/`category-manage-screen.tsx` (экран внутри таб-бара) против `pb-6` в `pick-account-screen.tsx` (модалка без таб-бара снизу). Разное значение здесь оправдано разным нижним системным элементом экрана, а не забывчивостью — не сводить к одному числу.

## I. Подсказки на основе истории операций (Smart defaults)

Там, где пользователь именно **совершает операцию** — создаёт новую транзакцию (расход/доход/перевод) или редактирует существующую, — приложение подсказывает наиболее вероятный выбор по истории, а не заставляет каждый раз выбирать из полного списка или брать дефолт по порядку в массиве. Это правило действует **только в момент ввода/редактирования транзакции** — на экранах, не связанных напрямую с самой операцией (фильтры Ленты, управление счетами/категориями, Настройки), всегда показывается полный список без сортировки по истории, чтобы не путать «недавно/часто использованное» с осмысленным списком для администрирования.

- **Категория при вводе расхода/дохода** — `CategoryPicker` показывает не все категории подряд, а `useFrequentCategories(kind)` (`src/features/add-transaction/model/use-frequent-categories.ts`): категории того же типа, отсортированные по числу использований за последние **30 дней**, топ-10 (`frequentCategoriesLimit`). Работает и при создании (`add-transaction-screen.tsx`), и при редактировании (`transaction-detail-screen.tsx`). Полный список без сортировки по частоте остаётся доступен отдельно — пункт «Все» → `pick-category`.
- **Счёт при вводе расхода/дохода** — по умолчанию не первый счёт по списку, а самый часто используемый **за последние 7 дней** в роли, соответствующей типу операции (`useFrequentAccountId`, `src/features/add-transaction/model/use-frequent-account-id.ts`): списание (`debit`) для расхода, зачисление (`credit`) для дохода. Раньше это был «последний использованный счёт» (отдельный сохранённый стор) — заменено на частоту за 7 дней, чтобы одна и та же логика ранжирования (`rankAccountsByRoleFrequency`, см. ниже) обслуживала и этот дефолт, и сортировку полного списка в `pick-account`, и подстановку пары для перевода, вместо трёх разных принципов.
- **Комбинация счетов при вводе перевода** — по умолчанию подставляется не первая пара счетов по списку, а самая частая пара «откуда → куда» среди переводов за последние **7 дней** (`findMostFrequentTransferPair`, `src/features/transfer/model/use-transfer-form.ts`). Если истории переводов нет — используются первые два счёта по списку, как раньше.
- **Список счетов в `pick-account`** — при открытии полного списка для выбора счёта под конкретную роль операции список сортируется по частоте использования счёта именно в этой роли за последние 7 дней (`rankAccountsByRoleFrequency`, `src/entities/transaction/model/account-role.ts`, используется из `src/pages/pick-account/ui/pick-account-screen.tsx`): самый часто используемый в этой роли счёт — первым, никогда не использованные в ней — в конце (в исходном порядке списка). Роль — `debit` (списание: счёт расхода, «Откуда» в переводе) или `credit` (зачисление: счёт дохода, «Куда» в переводе) — передаётся отдельным параметром навигации `role`, а не выводится из `requestId`: у `add-transaction`/`transaction-detail` один и тот же `requestId: 'account'` что для расхода, что для дохода, поэтому роль нужна отдельно, чтобы не перепутать «откуда обычно списываю» с «куда обычно зачисляю». `getRoleAccountId`/`rankAccountsByRoleFrequency` живут в `entities/transaction`, а не в `entities/account` — той же логике места, что и `useAccountBalance` (транзакции — исходные данные вычисления, счета — только его выход). Чтобы не заводить прямой импорт `entities/transaction` → `entities/account` между слайсами одного слоя, `rankAccountsByRoleFrequency` принимает счета структурно (`<T extends { id: string }>`), а не по типу `Account`, — как и `useAccountBalance` (`entities/transaction/model/use-account-balance.ts`), которая по той же причине принимает `{ id: string; initialBalance: number }` вместо `Account`.
- **Категория по тексту заметки при вводе расхода/дохода** — как только в поле заметки набрано слово от 3 букв, `CategoryPicker` вместо `useFrequentCategories` показывает `useNoteRelevantCategories(kind, note)` (`src/features/add-transaction/model/use-note-relevant-categories.ts`): категории ранжируются по побуквенному совпадению введённого текста с заметками прошлых операций того же типа (свой лёгкий алгоритм, не сторонняя fuzzy-библиотека — сумма пересечений букв по словам, с двойным весом за точное совпадение слова целиком). Пересчёт дебaunс-ится на 300мс, чтобы не гонять сравнение на каждое нажатие клавиши, а сам скан истории ограничен последними `noteMatchHistoryLimit = 500` операциями (`useTransactions()` уже отсортирован от новых к старым через `sortComparer` энтити-адаптера, так что это просто `.slice(0, 500)`) — без этого предела скан рос бы вместе с историей без потолка на много лет активного использования; 500 операций с запасом перекрывает год-два активности. Ограничение по количеству, а не по возрасту (в отличие от 7/30-дневных окон ниже) — намеренно: точное текстовое совпадение не «протухает» со временем (см. следующий пункт), поэтому старая, но точная заметка не должна терять шанс совпасть только из-за давности, а не из-за реального объёма истории. Если самая релевантная категория однозначно впереди второй (счёт минимум вдвое больше) — она подставляется автоматически, но только пока пользователь ещё не выбрал категорию сам (и в `transaction-detail` — только для новых, не для уже сохранённой на операции категории, см. `categoryManuallySetRef` в обоих экранах); любой ручной выбор эту автоподстановку окончательно отключает для текущей формы. Пока в заметке нет слов от 3 букв или совпадений в истории — список остаётся прежним, `useFrequentCategories`.
- **Окно анализа истории для частоты** — не одно значение на всё приложение, а два: **30 дней** — только у частых категорий (`frequencyWindowInDays`, `use-frequent-categories.ts`); **7 дней** (`accountFrequencyWindowInDays`, `entities/transaction/model/account-role.ts`) — у всего, что касается выбора счёта: дефолтный счёт при вводе расхода/дохода, сортировка `pick-account`, частая пара счетов перевода. Внутри каждой из этих двух групп окно остаётся единым — не вводить третье своё окно для нового места с похожей идеей без явной причины; если 7-дневное окно понадобится где-то ещё за пределами выбора счёта — переиспользовать `accountFrequencyWindowInDays`, а не заводить свою копию значения. Совпадение по тексту заметки (см. выше) — отдельное, намеренное исключение из обеих групп: оно смотрит на всю историю целиком, а не на N последних дней, потому что точное текстовое совпадение (тот же текст заметки, что и раньше) не «протухает» со временем так, как протухает частота использования — заметка про ипотеку, введённая год назад, всё ещё точный сигнал.
- Подсказка по истории — это ускорение самого частого пути, а не единственный вариант: рядом всегда остаётся явный способ выбрать что-то другое (полный список категорий за «Все», ручной выбор счёта через `pick-account`, свайп/тап по кнопке «поменять местами» в переводе) — ничего не должно быть недоступно только потому, что для него есть «умная» подсказка.
